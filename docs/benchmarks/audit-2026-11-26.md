## Findings (ranked)

### 1. 41% of input spend is unattributed — bug

323 calls, 14.48M input tok (41% of total), NULL task_id / NULL exploration_id /
empty worker, spread over 23 h. Current code labels every lane (intercept judge via
`llmrec.WithWorker` → `judgeWorkerLane`, chat parses the session id), so this row
shape should not exist. Suspects: intercept judge, chat, or a server-side caller
that bypasses the session context entirely.

Next step: enable LLM body recording (`llm_record` setting) for one heavy session,
reproduce the unattributed calls, then read `llm_records.request_body` — it
identifies the exact caller (system prompt text is a fingerprint).

### 2. Worker context bloat

`worker` lane: 592 calls, avg 32,780 input tok/call, max 75,497 — 19.4M tok total.
Cache-read absorbs most of the billing, but this drives latency, cache misses on
any prompt drift, and full-price input whenever caching breaks. Targets:
`graph_overview` prefetch size, tool output truncation, compaction thresholds.

Enable context telemetry (`ContextTelemetryEnabled` / `MeasureContext` in
`llmrec/llmrec.go`) to get the per-section breakdown of the 32K prompt.

### 3. Error burst — provider or retry storm

74 errors total; 67 inside the 2026-11-25 11:00 burst (734 calls / 22.4M tok in
one hour). Error avg latency 8.4 s vs ok 11.6 s. Input tokens on failed calls are
pure waste. Check `agent/llmretry` behavior + the failover pool config: cap
retries, add backoff, route failures to a second profile.

### 4. Cost-visibility gaps

- `cache_write` always 0: either the provider never reports writes (common with
  OpenAI-compatible relays) or the usage parser drops the field — verify in
  `agent/provider.go`.
- `llm_records` table completely empty: body recording was off. Without it there
  is no per-call debugging. Enable selectively (one task), not always — bodies
  are heavy.

## Optimization queue (derived)

1. **opt/fix-unattributed-usage** — find the NULL-attribution caller, fix labels;

   full task run.
2. **opt/context-slim** — worker avg input 32.8K → target ≤ 18K with same finding
   rate on the bench task.
3. **opt/retry-discipline** — error rate 7.5% → < 2%, bounded retries with backoff,
   failover to second profile.

## Resolution — finding 1 (2026-11-26)

Culprit identified: the chat family. Chat-page turns, conversation-agent runs
(server/conversations.go, session `conv-<id>`) and finding retests
(server/finding_retests.go) all run through ChatAgent.Chat; parseSession only
attributes `exp<N>-...` ids, so every such call was metered NULL. The 323 rows
were real conversation/agent turns, not phantom spend.

Fix: opt/fix-unattributed-usage — agent/chat.go now labels the lane
(worker = `chat`, or `conv:<agentKey>` for named conversation agents) and
carries the session id as the task label; connection tests labeled `conntest`
(agent/provider.go). Acceptance check: after deploying this build and running
chat + a conversation turn, `SELECT count(*) FROM llm_usage WHERE task_id IS
NULL` must stay flat outside intentional unlabeled callers.
